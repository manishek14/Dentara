# ADR-004: جدایی چرخهٔ وضعیت رزرو و پرداخت

- **Status**: Accepted
- **Date**: 2026-10-14
- **Decision Owner**: Architecture Team

## Context

در یک سامانهٔ رزرو با پرداخت آنلاین، دو فرایند مستقل وجود دارد:

1. **چرخهٔ رزرو**: رزرو ایجاد می‌شود → ظرفیت اشغال می‌شود → در صورت انقضا یا لغو، ظرفیت آزاد می‌شود.
2. **چرخهٔ پرداخت**: تلاش پرداخت ایجاد می‌شود → کاربر به درگاه می‌رود → callback می‌آید → در صورت موفقیت، رزرو تأیید می‌شود؛ در صورت شکست، بازپرداخت یا لغو.

این دو چرخه غالباً هم‌زمان هستند، اما همیشه هم‌زمان نیستند. چند سناریوی بحرانی:

- کاربر رزرو می‌کند، به درگاه می‌رود، اما مهلت ۱۰ دقیقه‌ای تمام می‌شود قبل از اینکه callback بیاید.
- کاربر پرداخت می‌کند، اما callback دیر می‌رسد (شبکهٔ درگاه کند است).
- کاربر پرداخت را دو بار انجام می‌دهد (retry مرورگر) و callbackهای متعدد می‌آید.
- کارگر پس‌زمینه رزرو را منقضی می‌کند، اما هم‌زمان callback موفقیت می‌رسد.

اگر این دو چرخه به‌صورت یک ماشین حالت واحد ادغام شوند، تعداد ترکیب‌ها به‌شدت زیاد می‌شود و حالت‌های غیرممکن (مثلاً "پرداخت موفق اما رزرو لغو شده") قابل تشخیص نخواهند بود.

## Decision

دو ماشین حالت مستقل نگه می‌داریم: **AppointmentStatus** و **PaymentStatus**. هر کدام چرخهٔ خود را دارد و تنها در نقاط مشخصی به هم متصل می‌شوند.

### ماشین حالت Appointment

| وضعیت | مصرف ظرفیت | توضیح |
|------|-----------|------|
| `PendingPayment` | بله (تا زمان انقضای معتبر) | رزرو ایجاد شده، در انتظار پرداخت |
| `Confirmed` | بله | پرداخت تأیید شده، رزرو قطعی |
| `Expired` | خیر | مهلت پرداخت تمام شده و پرداخت موفق نبوده |
| `Cancelled` | خیر | بیمار یا اپراتور لغو کرده |
| `Completed` | رزرو تاریخی | زمان شروع گذشته، خدمت ارائه شده |
| `NoShow` | رزرو تاریخی | زمان شروع گذشته، بیمار نیامده |

**انتقال‌های مجاز**:

- `PendingPayment` → `Confirmed` (پرداخت موفق)
- `PendingPayment` → `Expired` (انقضا با تأیید عدم پرداخت موفق)
- `PendingPayment` → `Cancelled` (لغو پیش از پرداخت)
- `Confirmed` → `Cancelled` (لغو پس از پرداخت → بازپرداخت)
- `Confirmed` → `Completed` (پایان خدمت)
- `Confirmed` → `NoShow` (زمان شروع گذشته بدون حضور)

### ماشین حالت Payment

| وضعیت | معنا |
|------|------|
| `Initiated` | تلاش پرداخت ایجاد شده، کاربر هنوز به درگاه نرفته |
| `Pending` | کاربر به درگاه رفته، callback هنوز نیامده |
| `Succeeded` | موفقیت با روش قابل‌اعتماد تأیید شده (callback معتبر یا verify مستقیم) |
| `Failed` | شکست قطعی تأیید شده |
| `Unknown` | نتیجه هنوز نامشخص است (timeout درگاه، شبکه قطع شده) |
| `RefundPending` | بازپرداخت درخواست شده |
| `PartiallyRefunded` | بخشی از مبلغ بازپرداخت شده |
| `Refunded` | مبلغ موردنظر کامل بازپرداخت شده |
| `RefundFailed` | عملیات بازپرداخت شکست خورده |

### نقاط اتصال دو ماشین

| رویداد | اثر روی Appointment | اثر روی Payment |
|--------|---------------------|-----------------|
| کاربر رزرو می‌کند | `PendingPayment` + ExpiresAtUtc | (هنوز نه) |
| کاربر به درگاه می‌رود | — | `Initiated` → `Pending` |
| callback موفق معتبر | `PendingPayment` → `Confirmed` | `Pending` → `Succeeded` |
| callback شکست قطعی | (تا انقضا در `PendingPayment` می‌ماند) | `Pending` → `Failed` |
| انقضای مهلت رزرو | `PendingPayment` → `Expired` | (اگر `Pending` → `Unknown` و سپس تطبیق) |
| لغو توسط بیمار (Confirmed) | `Confirmed` → `Cancelled` | `Succeeded` → `RefundPending` |
| تکمیل بازپرداخت | — | `RefundPending` → `Refunded` |

### حالت حساس: پرداخت نامعلوم

اگر مهلت رزرو تمام شود اما `PaymentStatus` هنوز `Pending` باشد:

1. رزرو به `Expired` منتقل **نمی‌شود** (ظرفیت آزاد **نمی‌شود**).
2. `PaymentStatus` به `Unknown` تغییر می‌کند.
3. Background Worker با درگاه **verify** می‌کند:
   - اگر موفق بود: رزرو به `Confirmed` منتقل می‌شود (حتی اگر دیر).
   - اگر قطعاً شکست خورده بود: رزرو به `Expired` و ظرفیت آزاد می‌شود.
4. اگر درگاه قابل‌دسترسی نبود: رزرو در `PendingPayment` می‌ماند تا زمانی که درگاه پاسخ دهد یا یک آستانهٔ زمانی طولانی (مثلاً ۲۴ ساعت) بگذرد و سپس به `Expired` برود.

این طراحی تضمین می‌کند که **هیچ‌گاه ظرفیت به دو بیمار فروخته نمی‌شود**، حتی اگر پرداخت دیرهنگام موفق شود. در حالت دیرهنگام، پرداخت وارد مسیر بازپرداخت دستی می‌شود.

## Alternatives Considered

### یک ماشین حالت واحد (مثلاً "Reservation" با وضعیت‌های ترکیبی)
- **مزیت**: یک جدول، یک state machine، ساده‌تر در ذهن.
- **دلیل رد**: تعداد ترکیب‌ها به‌شدت زیاد می‌شود (مثلاً `Confirmed_But_RefundFailed`، `Cancelled_But_RefundPending`). نگهداری transition table غیرعملی است. منطق کسب‌وکار قابل test نیست.

### استفاده از Event Sourcing
- **مزیت**: تاریخچهٔ کامل، replay capability.
- **دلیل رد**: overhead برای نسخهٔ اول. می‌توان بعداً روی همان schema event sourcing اضافه کرد با ثبت رویدادها در `AppointmentEvents` (که در ERD هست) بدون تغییر state machine اصلی.

### مدل Saga
- **مزیت**: مناسبMicroservices.
- **دلیل رد**: per ADR-002، monolith هستیم. تراکنش ACID یکپارچه کافی است.

## Consequences

### مثبت

- **تشخیص پذیری**: هر رزرو و هر تلاش پرداخت مستقل قابل ردیابی است.
- **ممیزی مالی**: تاریخچهٔ کامل `PaymentAttempts` + `Refunds` قابل بازیابی است.
- **پایداری در برابر پرداخت دیرهنگام**: ظرفیت هرگز به دو بیمار فروخته نمی‌شود.
- **قابلیت تست**: هر ماشین حالت به‌صورت مجزا unit-testable است.

### منفی

- **پیچیدگی عملیاتی**: support باید هر دو وضعیت را ببیند. UI باید آن‌ها را به‌صورت خوانا نمایش دهد.
- **مسیر "پرداخت نامعلوم" نیاز به monitor دارد**: اگر تعداد پرداخت‌های Unknown بالا برود، باید درگاه بررسی شود.
- **بازپرداخت دستی در حالت دیرهنگام**: تجربهٔ کاربر مطلوب نیست اما برای حفظ صحت سیستم ضروری است.

## Implementation Notes

- `PaymentAttempts` جدا از `Appointments` است. یک رزرو می‌تواند چند تلاش پرداخت داشته باشد (retry کاربر).
- `Refunds` جدا از `PaymentAttempts` است. یک تلاش پرداخت موفق می‌تواند چند بازپرداخت داشته باشد (مثلاً بازپرداخت جزئی اول، سپس تکمیل).
- `AppointmentEvents` هر تغییر وضعیت (رزرو یا پرداخت) را ثبت می‌کند تا replay و audit ممکن باشد.
